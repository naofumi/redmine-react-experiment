# React migration verification record

Use this record to answer two questions from the [charter](react-migration-charter.md). Can a user complete the same work in React? What did it take to move that workflow out of ERB?

## How to record a run

Before changing a workflow, run the steps on ERB and fill in the baseline column. Run them again on React from the same starting data. For each step, record the actual outcome and link the smallest piece of evidence that demonstrates it. For example, record the ordered issue IDs when checking a sort, or the values on the reopened issue when checking a save. A screenshot is useful when the location of a control affects the task.

| Run details | ERB baseline | React comparison |
| --- | --- | --- |
| Date and Git revision | Editor run on 2026-11-21 JST at `0b57b6a87` with Selenium and headless Chrome | Editor run on 2026-11-21 JST from the React working tree based on `0b57b6a87`, with Selenium and headless Chrome |
| Fixture or data setup, roles, and relevant settings | Editor used eCookbook issue #1 and a fresh copy of issue #1 for E5. Manager (jsmith) and Developer (dlopper) used their fixture permissions. E2–E4 narrowed the Manager’s New transitions for Feature request to Assigned and added the required Acceptance criteria field to that tracker. | Same editor fixtures, roles, and tracker rules as the ERB run |

Use **Untested** until the comparison has been run, **Pass** when the criterion holds, **Accepted difference** for an intentional change with a recorded reason and user impact, and **Regression** for an unintended loss of behavior. When a criterion changes, date the change and record why. Add rows in the same format before implementing later workflows.

## What the pilot establishes

Frontend changes to field arrangement, list rows, and group expansion now have React entry points. Changing a workflow rule or adding a query column still requires knowledge of Rails. The editor also retains Rails-rendered widgets for rich text, custom fields, time entries, and uploads. The list receives formatted cell content and uses the existing ERB filter form. Those are concrete limits on what a frontend engineer can change in TypeScript alone.

Much of the verification work came from existing controller tests that looked for controls in the first HTML response. They now inspect the data or widget markup Rails actually delivers. Browser tests cover what appears after React mounts, including the difference between cancelling the inline and standalone editors. The edit, refresh, validation, and save scenario also passed with Rails CSRF protection enabled.

The final combined headless Chrome run passed all nine tests in the editor, editor actions, and list migration files, with 186 assertions and no skips (seed `19752`). Type checking and the frontend build also passed.

The comparison covers the fixture roles and paths recorded above. Production rollout, usability with actual Redmine users, and the full application test suite remain unverified. A separate public API test stopped during Subversion repository setup on this machine, which lacks an available Subversion adapter. The same case stopped at the same fixture on the original ERB revision before reaching its assertion. [API test](../test/integration/api_test/issues_test.rb#L523)
